# 0.3.0-preview.1 预览交付

定位：面向开发者与 Coding Agent 的可恢复任务框架。通过独立业务包接入业务，复用任务、权限、审批、渠道与运行治理。当前为开发者预览候选，不承诺生产 SLA；源码/SDK 制品不代表已经发布到 GitHub、npm 或镜像仓库。

## 接入与验收

先走 [最短教程](getting-started.md)，然后按业务选择扩展。保持 core 不变，通过包与适配器实现领域规则。

| 场景 | 改动位置 | 本地验证证据 | 外部试用验收 |
| --- | --- | --- | --- |
| 人工确认后执行工具 | 新包源码、宿主包清单、配置和权限 | `tests/tutorial.test.ts` 直接执行教程代码，验证权限、重启接管、批准/拒绝和重放 | 独立接入者从干净 checkout 完成教程，记录阻塞步骤、耗时、核心修改文件数 |
| 连接读取、模型处理、文件交付 | 包内编排与工具、依赖绑定、供应商适配器 | `tests/evolution-adapters.test.ts` 的中立 pipeline 测试与 `pnpm sdk:verify` 的外部工程安装 | 接入方使用自有测试服务，验证凭据轮换、超时、取消、权限和产物；记录供应商/模型及脱敏结果 |

上述本地场景不冒充两个外部团队的真实业务试用。外部试用报告请包含：来源提交、运行环境、业务类型、修改文件、是否修改核心、首任务耗时、阻塞点和验收结果。不能仅凭 SDK 编译成功判断改造便利性。

## 发布者执行顺序

1. 根据 [开发验证](development.md#验证) 完成最终源码的格式、check、SDK、契约、离线评测、镜像及隔离 Compose 验收。修改迁移不得跳过受限运行角色测试。
2. 从干净提交执行 `pnpm release:prepare && pnpm release:verify`。候选目录 `dist/release/` 包含源码、SDK tarball、SBOM、来源提交与 SHA-256 清单；可整体交付，不依赖本机 Golutra 或参考项目。
3. 首次公开前独立审计 Git 历史。当前源码扫描不能替代历史审计；如使用源码归档建立全新公开仓库，应保留候选来源清单和许可。
4. 在实际目标仓库配置私密漏洞报告和分支保护，在对应提交跑托管 CI，再创建版本标签和预览 Release，上传候选文件。SDK 可先以 tarball 分发，未取得 npm scope 或镜像目标时不承诺公开安装命令。
5. 收集上表两个不同业务的外部试用报告，按实际阻塞点决定下一轮优化。

本地候选生成不自动推送、创建远端仓库、发布 npm 或发送试用邀请。真实外部试用需要接入方和测试服务；没有这些信息时，交付状态应明确标为“本地候选已验收，公开发布/外部试用待完成”。

## 升级与兼容

迁移追加到 029；已有部署按 [升级步骤](operations.md#升级) 停止旧 Worker、备份、运行迁移/provision 并重启兼容实例。已有完成步骤保持复用。中间模型检查点请求指纹升级后可能重新计算，旧已知费用和耗时继续计入预算。

SDK major 1 保持不变，`restoreSourceRanges` 增加可选 `{coverage:"full"}`。默认局部摘录兼容；倒置、小数、越界或重叠范围现在拒绝，输出换行统一为 LF。Pi 的推理参数、SDK 缓存和网关取消限制见 [模型接入](extending.md#可选上下文与模型结果)。
